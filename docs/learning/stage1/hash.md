## 1. 전체 구조 — 디렉터리 → 버킷 2단

```
key ──mix──▶ 해시(64비트) ──하위 global_depth 비트(& mask)──▶ 디렉터리 칸 번호
                                                             │
global_depth = 2 일 때:                                      ▼
  디렉터리 (길이 2^2 = 4)          버킷들
  칸 00 ──────────────▶ 버킷 A (local_depth 2)  ← 해시 하위 비트 00
  칸 01 ──┐
          ├───────────▶ 버킷 B (local_depth 1)  ← 해시 하위 비트 …1
  칸 11 ──┘
  칸 10 ──────────────▶ 버킷 C (local_depth 2)  ← 해시 하위 비트 10
```

| 이름 | 뜻 |
|---|---|
| `global_depth` (전역 깊이) | 디렉터리가 해시 하위 **몇 비트**를 보나. 디렉터리 길이 = **2^global_depth** (깊이 +1 → 칸 **두 배**) |
| `local_depth` (지역 깊이) | 그 버킷이 실제로 몇 비트로 키를 구분하나. ≤ 전역 깊이(I3) |
| 칸 공유 | 지역 < 전역이면 위쪽 비트만 다른 **2^(전역−지역)** 칸이 한 버킷을 같이 가리킨다(위 B: 2^(2−1) = 2칸) |
| `BucketId` | 버킷 배열 번호 — B+tree의 `NodeId`처럼 2단계에서 페이지 번호가 된다 |

처음 상태: 전역 깊이 0 · 디렉터리 `[0]` 1칸 · 빈 버킷 1개.

## 2. `get` — 칸 번호 만들기 3단계

```rust
pub fn get(&self, key: u64) -> Option<u64> {
    let b = &self.buckets[self.directory[self.slot(key)]];          // 칸 → 버킷 번호 → 버킷
    b.keys.iter().position(|&k| k == key).map(|i| b.values[i])     // 버킷 안은 순서 없음 → 앞부터
}

fn slot(&self, key: u64) -> usize {
    let mask = (1u64 << self.global_depth) - 1;   // ① 자 만들기
    (mix(key) & mask) as usize                    // ② 섞기 → ③ 자르기
}
```

| 단계 | 하는 일 | 대상 |
|---|---|---|
| ① `(1 << d) - 1` | 하위 d비트가 전부 1인 **자** (d=2 → `0b11`, d=3 → `0b111`) | 깊이 `d`만 — 키와 무관 |
| ② `mix(key)` | 키 비트를 뒤섞어 **해시** | 키 |
| ③ `& mask` | 해시의 하위 d비트만 남김 = 칸 번호 | ②의 결과 |

## 3. `mix` — 왜 키를 그대로 쓰지 않나 (T8)

```rust
fn mix(key: u64) -> u64 {   // splitmix64 마무리 단계
    let mut z = key;
    z = (z ^ (z >> 30)).wrapping_mul(0xbf58_476d_1ce4_e5b9);
    z = (z ^ (z >> 27)).wrapping_mul(0x94d0_49bb_1331_11eb);
    z ^ (z >> 31)
}
```

- **비트를 뒤섞는다** → 규칙 있는 키(8의 배수·연속 수)도 하위 비트가 0/1 반반쯤으로 퍼진다.
- **전단사** → 다른 키는 해시도 반드시 다르다 → 분할을 거듭하면 언젠가 반드시 갈라진다(디렉터리 무한 두 배 불가).

### 실계산 — 버킷 용량 2에 8, 16, 24 삽입 (diff 08 미리보기)

키 그대로 (하위 비트 8=`1000`, 16=`0000`, 24=`1000`):
```
d=0 [ 8,16 ] ← 24 넘침
d=1  하위 1비트: 0    0    0     여전히 한 버킷 → 또 넘침
d=2  하위 2비트: 00   00   00    또 넘침
d=3  하위 3비트: 000  000  000   또 넘침
d=4  하위 4비트: 1000 0000 1000  → {8,24} / {16}
```
키 3개에 디렉터리 1칸 → **16칸**, 쓰는 버킷은 2개.

`mix` (하위 비트 8=`…1000`, 16=`…1101`, 24=`…1000`):
```
d=0 [ 8,16 ] ← 24 넘침
d=1  하위 1비트: 0  1  0  → {8,24} / {16}  끝 (2칸)
```
운이 나쁘면 몇 번 더 겹칠 수도 있다(32와 40은 mix 하위 3비트가 둘 다 `101`, 4비트째에서 갈림) — 그래도 전단사라 64비트 안에서 반드시 갈라진다.

## 4. 모듈 연결 — `pub mod hash;` (diff 07b)

```
src/lib.rs        ─ pub mod index; ──▶ src/index/mod.rs
src/index/mod.rs  ─ pub mod btree; ──▶ src/index/btree.rs
                  ─ pub mod hash;  ──▶ src/index/hash.rs   ← 07b
```

- 컴파일러는 `src/`의 .rs를 전부 읽지 않는다 — `lib.rs`에서 `mod` 선언을 따라간 파일만 연다.
- `mod hash;` = 파일을 모듈 트리에 붙임 → **컴파일 대상 여부**. 없으면 디스크에만 있는 고아 파일 — 문법 오류가 있어도 `cargo test`·clippy가 통과한다(그래서 07a는 스크래치 사본에 선언을 넣어 따로 검증했다).
- `pub` = 바깥(다른 crate·3단계 러너)에서 `index_lab::index::hash::Hash`로 쓸 수 있나 → **공개 여부**. 없어도 컴파일은 된다.

## 4-1. `insert`·`split` — 넘치면 나누기 (diff 08)

```rust
pub fn insert(&mut self, key: u64, value: u64) -> Option<u64> {
    // 같은 키가 있으면 값만 바꾸고 이전 값 반환(upsert)
    b.keys.push(key);
    b.values.push(value);
    loop {                                       // 넘치면 나누기를 반복
        let id = self.directory[self.slot(key)]; // key가 든 버킷을 매번 다시 찾는다
        if self.buckets[id].keys.len() <= self.bucket_cap {
            return None;
        }
        self.split(id);
    }
}

fn split(&mut self, id: BucketId) {
    let d = self.buckets[id].local_depth;
    if d == self.global_depth {                  // 나눠 줄 칸이 없다 → 디렉터리 두 배
        self.directory.extend_from_within(..);  // 뒤 절반 = 앞 절반 복사
        self.global_depth += 1;
    }
    let bit = 1u64 << d;                         // 새로 보는 비트 = d번째
    // 키를 꺼내 mix(k) & bit 가 0이면 stay, 1이면 moved (둘 다 지역 d+1)
    // buckets[id] = stay, buckets.push(moved) → new_id
    for (slot, b) in self.directory.iter_mut().enumerate() {
        if *b == id && slot as u64 & bit != 0 {  // 이 버킷을 가리키던 칸 중 새 비트가 1인 칸
            *b = new_id;
        }
    }
}
```

### 두 경우

시작 상태(전역 2): 칸 00 → A(지역 2) · 칸 01, 11 → B(지역 1) · 칸 10 → C(지역 2)

**① B 넘침 — 지역 1 < 전역 2 → 디렉터리 그대로, 칸만 다시 가리킴**
```
분할 전            분할 후 (새 비트 = 1번 비트)
칸 01 → B          칸 01 → B   (지역 2)   ← 1번 비트 0
칸 11 → B          칸 11 → B'  (지역 2)   ← 1번 비트 1
```
B를 가리키던 2^(전역−지역) = 2칸 중 새 비트가 1인 절반만 새 버킷으로.

**② A 넘침 — 지역 2 = 전역 2 → 디렉터리 두 배 후 나눔**
```
두 배 (뒤 절반 = 앞 절반 복사), 전역 3:
칸 000 → A    칸 100 → A   ← 복사본
칸 001 → B    칸 101 → B
칸 010 → C    칸 110 → C
칸 011 → B'   칸 111 → B'
그다음 A를 2번 비트로 나눔:  칸 000 → A, 칸 100 → A'
```

### 복사해도 되는 이유
두 배 직후의 새 최상위 비트(위에선 2번 비트)는 **아직 어떤 버킷도 보지 않는다**(모든 지역 깊이 ≤ 이전 전역 깊이). 그래서 그 비트만 다른 두 칸(`001`/`101`)은 모든 버킷 입장에서 같은 칸 → 같은 버킷을 가리키는 게 맞다. 두 배 순간에 **옮겨지는 키는 0개** — 키는 그다음 넘친 버킷 하나를 나눌 때만 움직인다.

### 해시 버킷엔 next/prev가 없다

| | B+tree 리프 분할 | 해시 버킷 분할 |
|---|---|---|
| 새 노드/버킷을 끼우는 방법 | 형제 `next`/`prev` 재연결 + 부모에 구분자 | **디렉터리 칸이 가리키는 번호를 바꿈** |
| 이웃끼리 연결 | 있음(양방향) | 없음 |
| 그래서 range는 | 링크를 따라 순서대로 | 전체를 훑어야 함(diff 09, T10) |

### `loop` 따라가기 — 용량 2에 16, 32, 40 (실행 결과와 일치)

mix 하위 4비트: 16 = `1101`, 32 = `0101`, 40 = `0101`. 처음 버킷 #0에 16, 32가 있고 40을 넣어 3개 → 넘침.

| 분할 | 나누는 버킷(지역 d) | 디렉터리 | 새 비트(d번) 값 16/32/40 | 결과 | 다시 넘침? |
|---|---|---|---|---|---|
| 1 | #0 (d=0 = 전역 0) | 두 배 → 2칸 | 1 / 1 / 1 | 셋 다 새 버킷 #1 | #1에 3개 → 예 |
| 2 | #1 (d=1 = 전역 1) | 두 배 → 4칸 | 0 / 0 / 0 | 셋 다 #1에 남음, 새 #2는 빈 버킷 | 예 |
| 3 | #1 (d=2 = 전역 2) | 두 배 → 8칸 | 1 / 1 / 1 | 셋 다 새 버킷 #3 | 예 |
| 4 | #3 (d=3 = 전역 3) | 두 배 → 16칸 | **1 / 0 / 0** | {32,40} #3 · {16} 새 #4 | #3에 2개 → 아니오, 끝 |

최종: 전역 4, 디렉터리 `[0,1,0,2,0,3,0,2,0,1,0,2,0,4,0,2]` (스크래치 실행 출력과 같음).

- **문제의 원인은 디렉터리 링크가 아니라 키들의 해시 비트가 아래쪽에서 같다는 것.** 새 비트 하나로 나눌 때 그 비트가 모두 같으면 전부 한쪽으로 가서 또 넘친다. 디렉터리는 그 비트를 보기 위해 따라 커질 뿐이다.
- 이건 버그가 아니라 Extendible Hash의 정상 동작이고, `loop`가 바로 그 경우를 처리한다. 대가: 빈 버킷(#0·#2)과 커진 디렉터리.
- 매 반복에서 나눌 버킷은 `self.directory[self.slot(key)]` — 방금 넣은 key가 든 버킷 — 로 다시 찾는다. 다른 쪽은 그 부분집합이라 넘칠 수 없다.
- `mix`가 전단사라 64비트 안 어딘가는 반드시 다르다 → loop는 반드시 끝난다.

## 4-2. `range`·`range_rev` — 전부 훑고 정렬 (diff 09a)

```rust
pub fn range(&self, lo: u64, hi: u64) -> Vec<(u64, u64)> {
    let mut out: Vec<(u64, u64)> = self.buckets.iter()
        .flat_map(|b| b.keys.iter().copied().zip(b.values.iter().copied()))
        .filter(|&(k, _)| lo <= k && k <= hi)
        .collect();
    out.sort_unstable_by_key(|&(k, _)| k);
    out
}
pub fn range_rev(&self, lo: u64, hi: u64) -> Vec<(u64, u64)> {
    let mut out = self.range(lo, hi);
    out.reverse();
    out
}
```

**왜 전부 훑나** — 연속 키도 `mix` 뒤엔 흩어진다(전역 3, 하위 3비트):

```
키      30    31    32    33
칸     010   101   101   111
```

30이 든 칸 "옆"에 31이 있지 않고, 버킷 사이엔 B+tree 리프의 `next` 같은 연결도 없다 → "lo에서 시작해 읽기"가 불가능 → 모든 버킷을 훑어 `lo <= k <= hi`만 거른다.

**왜 마지막에 정렬하나** — 버킷엔 해시값이 아니라 **원래 키**가 저장된다(`b.keys.push(key)`). `mix`는 칸·버킷을 고를 때만 쓴다. 그러니 되돌리는 단계 없이 `k`로 바로 정렬하면 된다. 정렬이 *필요한* 이유는 모이는 순서가 `버킷 번호 순(= 분할로 생긴 순서, new_id = buckets.len()) + 버킷 안 push 순서(= 넣은 순서)`라서 키 크기와 무관하기 때문이다. trait(`mod.rs`)는 오름차순을 약속한다. 키 중복이 없으니 불안정 정렬로 충분.

**왜 뒤집기만 하나** — `range` 결과가 이미 오름차순이니 `reverse()`가 곧 내림차순. 해시엔 hi에서 거꾸로 걷는 더 싼 길(출발점·연결)이 없고 어차피 전체 훑기+정렬이라, 따로 구현할 이득이 없다.

| | B+tree | Hash |
|---|---|---|
| range 시작 | `find_leaf(lo)`로 바로 내려감 | 출발점 없음 — 전체 버킷 |
| 다음 키 | 리프 `next` | 연결 없음 |
| 순서 | 리프가 이미 정렬 | 모은 뒤 정렬 |
| range_rev | `prev` 따라 필요한 만큼 | `range` 결과 뒤집기 |
| 비용 | 높이 + 결과 크기 | 항상 n + 정렬 |

`impl super::Index for Hash`는 네 메서드를 `Hash::…`에 그대로 위임 — 3단계 러너가 `Box<dyn Index>`로 B+tree와 바꿔 끼운다.

## 4-3. `check()`와 테스트 (diff 09b — 블라인드 설계)

테스트는 구현 본문을 보지 않은 워커가 명세(I3)에서 출발해 설계했다(B+tree diff 06과 같은 방식).

**공개 API (T12)**: `global_depth()` · `bucket_count()` · `check()` — 테스트와 3단계 실험이 같이 쓴다.

**`check()`가 보는 것 (I3)**

| 검사 | 예: 전역 3, 버킷 R 지역 1, 접미사 1 |
|---|---|
| 디렉터리 길이 = 2^전역 | 8칸 |
| 모든 칸이 있는 버킷을 가리킴 | — |
| 지역 ≤ 전역 | 1 ≤ 3 |
| 가리키는 칸 수 = 2^(전역 − 지역) | 2^(3−1) = 4칸 |
| 그 칸들의 하위 d비트가 같음 | `001 011 101 111` |
| 버킷 안 키: `mix(k) & mask` = 접미사 | 키 30: `k & 0b111` = 110 ✗ / `mix(30) & 0b111` = 010 ✓ |
| 키·값 수 같음 · 키 수 ≤ 용량 · 전체 키 중복 없음 | — |
| 아무 칸도 안 가리키는 버킷 = 위반 | 삭제가 없으니(T4) 생길 이유가 없다 |

**왜 `mix(k)`를 다시 계산하나** — 버킷엔 **원래 키**가 저장된다(`push(key)`). 칸 번호는 `mix(key) & mask`로 정해졌으니, 검사도 같은 기준(`mix`)으로 맞춰야 한다. `k & mask`로 비교하면 제자리에 있는 키도 위반으로 잡힌다.

**`check()` 자체 검증 — 일부러 망가뜨리기 10종** (`#[should_panic(expected = "…")]`로 *어느* 검사가 터져야 하는지까지 지정)

예: `check_catches_wrong_directory_pointer` — 지역 = 전역(칸 1개씩 받는) 두 버킷 P(`000`)·Q(`100`)의 칸을 맞바꾼다.
- 칸 수: P를 가리키는 칸 1개 = 2^(3−3) → **통과**(칸 수 검사로는 못 잡음)
- 키 검사: P 키들의 `mix` 하위 3비트 `000` ≠ 새 접미사 `100` → **터짐**

**proptest 2개**

| | `matches_btreemap` | `structure_holds_after_every_insert` |
|---|---|---|
| 용량 · 삽입 | 2..=4 · ≤300 | 2..=4 · ≤120 |
| `check()` | 끝에서 1회 | **삽입마다** — 깨진 삽입을 바로 짚는다 |
| 대조 | insert 반환·get·range·range_rev·`&dyn Index` vs BTreeMap | insert 반환·get · 깊이/버킷 수 줄지 않음 · upsert는 구조 불변 |

**용량을 2..=4로 잡은 이유**: 1이면 디렉터리가 깊어지고(전역 15 → 32768칸) 매 삽입 `check()`가 그걸 다 훑어 느리다. 100처럼 크면 분할이 거의 안 일어나 정작 검증할 분할·두 배 로직을 못 건드린다.

## 4-4. 변이 점검 (diff 10) — 일부러 틀리게 바꾸면 테스트가 잡나

스크래치 사본에서 한 줄씩 틀리게 바꾸고 `cargo test` → 원복(레포 코드 무변경).

| 변이 | 바꾼 곳 | 실패 테스트 | 왜 잡히나 |

H2는 `matches_btreemap`의 축소(shrink)에 ~110초가 걸렸다 — 실패를 찾는 건 빨랐고 최소 사례로 줄이는 데 시간이 든 것.

### `check()`는 무엇인가 (사용자 질문: "check는 무슨 역할인데 자꾸 나오는 거야?")

`insert`·`get`·`range` 같은 기능이 아니라 **구조가 망가지지 않았는지 보는 테스트용 검사기**(09b에서 추가). 사서가 책장을 돌며 모든 책이 *꽂혀 있어야 할 자리*에 있는지 보는 일 — 책 = 키, 자리 = `mix(키)`로 정한 칸. `split`이 칸을 잘못 다시 가리키면(H1·H2) 키가 엉뚱한 버킷에 남아 `get`이 못 찾는데, 그걸 바로 잡아낸다.

### 저장 vs 위치 — 실제 출력 (용량 2, 키 30~33)

```
global_depth = 2
directory = [0, 1, 0, 2]
bucket 0 (local 1): keys = [30]
    key 30  mix(key) = 0x0724ea9269d42a72  low 3 bits = 010
bucket 1 (local 2): keys = [31, 32]
    key 31  mix(key) = 0x540f172e046ef165  low 3 bits = 101
    key 32  mix(key) = 0xadfb1ebb497fad45  low 3 bits = 101
bucket 2 (local 2): keys = [33]
    key 33  mix(key) = 0xb4941eef820868c7  low 3 bits = 111
range(30,33) = [(30, 300), (31, 310), (32, 320), (33, 330)]
```

| 쓰는 곳 | 쓰는 값 |
|---|---|
| 저장 | 원래 키 (`push(key)`) |
| `insert`·`get`이 칸 찾기 | `mix(key)` |
| `range` 정렬 | 원래 키 |
| `check()` 제자리 검사 | 원래 키를 꺼내 → `mix` 다시 계산 → 칸 접미사와 비교 |

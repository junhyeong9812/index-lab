## 1. 내부 노드 분할 Q&A

### Q1. 키가 4개인데 자식은 왜 5개인가?

키는 자식과 자식 **사이의 칸막이**다. 칸막이 4개를 그으면 칸은 5개가 생긴다.

```text
        30        50        70        90          ← 키 4개 = 칸막이
  ──────┼─────────┼─────────┼─────────┼──────
   L0       L1        L2        L3       L4       ← 자식 5개 = 칸
  <30    30~49     50~69     70~89     90 이상
```

- 맨 왼쪽(`<30`)·맨 오른쪽(`90 이상`) 칸은 한쪽이 열려 있어서 칸이 칸막이보다 항상 1개 많다 → **키 n개 = 자식 n+1개**.
- 코드: `i = keys.partition_point(|&sep| sep <= key)` 는 0~4의 5가지 값 → `children[i]` 가 5개 있어야 한다. 4개뿐이면 95를 찾을 때 `children[4]` 범위 초과(panic).
- 어떻게 5개가 됐나: 루트 분할 때 `키 [30] · 자식 [L0, L1]`(1·2)로 시작 → 리프가 갈라질 때마다 부모는 **키 1개 + 자식 1개를 함께** 받는다 → 2·3 → 3·4 → 4·5. 차이 1이 계속 유지된다.

### Q2. 분할 설명에서 키·자식 개수가 안 맞아 보인다

`split_internal`은 키를 먼저 자르고 자식은 나중에 자르므로 **중간 단계에서만 잠깐 어긋난다.** 함수가 끝나면 맞는다.

| 단계 | N의 keys | N의 children | 맞나? |
|---|---|---|---|
| 넘친 상태 | [30, 50, 70, 90] (4) | [L0..L4] (5) | ✅ |
| `keys.split_off(3)` 직후 | [30, 50, 70] (3) | 5 그대로 | ❌ 잠깐 |
| `keys.pop()` 직후 | [30, 50] (2) | 5 그대로 | ❌ |
| `children.split_off(3)` 직후 | [30, 50] (2) | [L0, L1, L2] (3) | ✅ |

새 노드 N' = keys `[90]`(1) · children `[L3, L4]`(2) ✅

```text
전체 보존:  키   4 = N 2 + N' 1 + 위로 1(70)
            자식 5 = N 3 + N' 2
부모:       (70, N')을 받아 keys +1 · children +1 → 부모도 n+1 유지
```

### Q3. 70은 부모로 올라가는 게 맞지 않나?

맞다. 다만 **자식은 하나도 올라가지 않는다.** 5개 전부 아래에 남아 70의 자리를 기준으로 둘로 나뉜다.

```text
        30        50       [70]       90
  ──────┼─────────┼─────────┃─────────┼──────
   L0       L1        L2    ┃   L3       L4
  └──────── 왼쪽 N ─────────┘└──── 오른쪽 N' ───┘

              [70]               ← 이제 "N이냐 N'냐"를 가르는 칸막이
            /      \
     [30 | 50]      [90]
     L0  L1  L2     L3  L4
```

- 70은 아래에서 "L2냐 L3냐"를 가르던 칸막이 → 위에서는 같은 자리에서 "N이냐 N'냐"를 가른다. 아래에 남기면 같은 칸막이가 두 번 생긴다 → **이동(push-up)**.
- 리프 분할의 구분자(예: 30)는 **값이 달린 데이터**라서 리프에 남기고 복사본만 올린다(copy-up). 내부의 70은 칸막이일 뿐이라 그대로 옮긴다.

### Q4. "상위 노드의 공간 자체가 자식 구간이고, 70의 자식은 왼쪽이라 닫는 구간 자식이 된다"?

앞부분이 핵심이다 — **내부 노드 = 수직선을 칸으로 나눈 지도, 자식 = 칸 하나, 키 = 칸막이.**
정정 한 가지: **키 70 자체는 오른쪽 칸에 속한다.**

```text
              50        70        90
   ───────────┼─────────┼─────────┼────
       L1         L2    │    L3
              50 ≤ k < 70 │ 70 ≤ k < 90
                      열린 끝 │ 닫힌 시작
```

- 규칙 **왼쪽 < 구분자 ≤ 오른쪽**. `partition_point(|&sep| sep <= key)`에서 key = 70이면 `70 <= 70` 참 → 칸막이를 넘은 것으로 세어 오른쪽으로.
- 그래서 실제 값 70은 L3 쪽 리프 `[70, 80]`에 있다.
- 리프 분할 때 "오른쪽 리프의 **첫 키**"를 구분자로 올리는 이유도 이것 — 구분자 = 오른쪽 칸의 닫힌 시작점.

| 내용 | 판정 | 정답 |

**정답 요약 (diff 04)**

```text

 children.split_off(3) → N [L0,L1,L2] / N' [L3,L4]
반환 (70, N')  ← split_leaf와 같은 Split 모양 → 부모·insert 코드 그대로 재사용
```

## 2-1. 범위 읽기 Q&A (diff 05)

### Q5. 역순(`range_rev`)은 왜 만드나? 정순으로 찾고 뒤집으면 같지 않나?

결과는 **같다**(스모크로 확인). 차이는 **끝까지 다 읽어야 하느냐**다.

```sql
SELECT * FROM orders WHERE id <= 1000000 ORDER BY id DESC LIMIT 10;   -- 최신 10개
```

| 방법 | 읽는 양 |
|---|---|
| 정순 `range(0, 1000000)` → 뒤집기 → 10개 | 100만 개를 **전부** 읽어야 마지막 10개를 안다 |
| 역순 `find_leaf(1000000)`에서 `prev`로 10개 | 리프 **한두 개** |

- 명세 근거: T7(양방향 리프 — InnoDB·PostgreSQL 모두 양방향, 역방향 스캔에 사용), T13(`range_rev`를 trait에 — Hash와의 실험 축).
- ⚠️ 지금은 `Vec`으로 전부 모아 돌려주므로 "10개만 읽고 멈추기"는 아직 못 한다 — 차이가 숫자로 드러나는 건 짧은 범위 실험이나 iterator화 이후(NEXT 후보).

### Q6. `C.prev`는 왜 꼭 고쳐야 하나? A는 그대로 C를 봐도 되지 않나?

링크 4개는 **두 쌍**이고 각 쌍이 한 방향 읽기를 책임진다.

| 방향 | 책임 링크 | 안 고치면 |
|---|---|---|
| 정순 `next` (`range`) | `A.next = A'`, `A'.next = C` | `range`가 A'를 건너뜀 |
| 역순 `prev` (`range_rev`) | `C.prev = A'`, `A'.prev = A` | `range_rev`가 A'를 건너뜀 |

```text
A.next를 안 고치면:   A ──next──▶ C        (A'로 들어가는 next 길이 없음)
                          A' ──next──▶ C
C.prev를 안 고치면:   A ◀──prev── C        (A'로 들어가는 prev 길이 없음)
                      A ◀──prev── A'
```

- 각 방향 체인에서 A'로 들어가는 길은 **딱 하나**(next 쪽은 A.next, prev 쪽은 C.prev) → 하나라도 옛 이웃을 가리키면 그 방향에서 A'가 통째로 사라진다.
- 불변식 I2: next로도 prev로도 모든 키를 한 번씩 · `a.next = b` ⇔ `b.prev = a`.
- 단방향(`next`만)이었다면 `C.prev`도 없다 — 양방향의 대가 = 분할 때 C 한 번 더 쓰기(2단계에서 페이지 쓰기 +1로 측정).

### diff 05 게이트 기록

**1차 (fail 1/2)**
> lo에서 시작해서 hi까지 탐색하고 hi를 만나면 멈추네. / rev는 hi에서 리프를 찾도록 하네. / … C.prev가 없으면 해당 키 값이 빠지게 됬겠지.

| 내용 | 판정 | 정답 |
|---|---|---|
| 시작점 lo / hi | ✅ | `find_leaf(lo)` / `find_leaf(hi)` |
| 무엇을 따라가나 | 빠짐 | `range`는 `next`, `range_rev`는 `prev` |
| "hi를 만나면 멈춘다" | ✗ 부정확 | **hi보다 큰 키**에서 멈춘다 — hi와 같은 키는 포함(양끝 포함 `[lo, hi]`, T14) |
| 내부 노드 횟수 | 빠짐 | 루트→리프 **한 번** 내려가고(높이만큼 내부 노드 통과), 이후 리프 링크만 |
| "키가 빠진다" | 일부 | **A'의** 키가, C.prev가 여전히 A를 가리켜 **A'를 건너뛰기** 때문. 정순은 영향 없음 |

**2차 (PASS) — 하나씩 질의**
> ① range는 lo 리프에서 시작해 next 따라가고 hi보다 큰 키에서 멈춰
> ② prev 따라가고 내림차순으로 나오고 lo보다 작은 키에서 멈춰
> ③ 내부로는 2번, 리프를 옮길 때는 리프에서 바로 이동
> ④ C.prev는 A를 가리켜서 A' 건너뛰고 A' 키 빠짐, range는 영향 없음

보충: ③의 "2번" = 한 번 내려가며 내부 노드 2개(`[70]`, `[30|50]`)를 지난 것. 트리가 깊어지면 지나는 수는 높이만큼 늘지만 내려가는 건 여전히 한 번. ①은 체인 끝(`next == None`)에서도 멈춘다.

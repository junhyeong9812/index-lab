## 다음 작업 후보 (우선순위순)

### N1. 로드맵 2단계 — Pager + 버퍼풀, 인덱스를 페이지 위로 — 우선순위: 높음 · README 로드맵 순서

- **왜 다음인가**: 1단계가 2단계를 전제로 설계됨 — B+tree `NodeId`(arena 번호, T5)와 Hash `BucketId`가 그대로 `PageId`가 될 자리.
- **발생 가능한 문제** (1단계 관측 신호):
  - `range`가 `Vec`를 돌려준다(T1) → 페이지 위에서는 결과 전체를 만든 뒤에야 반환, 중간에 멈출 수 없음. 버퍼풀 빌림 수명과 반복자를 섞으면 T1에서 피했던 문제가 다시 온다.
  - Hash `split`의 칸 재지정이 디렉터리 전체를 훑는다(`hash.rs` ponytail 주석, O(2^전역)) → 디렉터리가 페이지에 오르면 분할 1회 = 디렉터리 페이지 전부 읽기·쓰기.
  - B+tree 리프 분할 시 오른쪽 형제 `prev` 갱신(T7) = 페이지 쓰기 +1 — 측정 대상으로 남겨 둠.
  - 매 삽입 `check()`가 O(구조 크기) — 페이지 I/O가 붙으면 속성 테스트가 더 느려진다(이번에 debug·cap 1에서 120s 초과 관측).
- **방법론 선택지**:

| 방안 | 요지 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|----------|----------|
| A | `range`는 `Vec` 유지, 페이지만 도입 | 작음 | 범위 조회 조기 종료 불가 — 3단계 측정이 결과 크기에 묶임 | 2단계 범위를 Pager·버퍼풀에 집중할 때 |
| B | 페이지 핀을 쥔 반복자(`range_iter`) 추가 | 중간~큼 | 빌림 수명·핀 해제 누락 | 3단계에서 "결과 k개만" 실험이 필요할 때 |

- **권장 대처**: A로 시작하고, 반복자는 3단계 실험 설계가 요구할 때 별도 작업으로. Hash 칸 재지정은 분할 비용을 측정한 뒤 "그 버킷을 가리키는 칸만 골라 돌기"로 바꿀지 판단.
- **착수 전 확인할 것**: 페이지 크기·버퍼풀 교체 정책(LRU/Clock) 사용자 선택 · 디스크 파일 vs 메모리 가짜 디스크 · load-bearing 가정: 노드/버킷이 한 페이지에 들어가는 최대 키 수 계산.

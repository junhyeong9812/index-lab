## 다음 작업 후보 (우선순위순)

### N1. 로드맵 3단계 — 벤치마크 하네스, 기본 격자 실험 — 우선순위: 높음 · README 로드맵 순서

- **왜 다음인가**: 2단계로 두 인덱스가 같은 버퍼풀·Pager 위에 올라 read/write/hit/miss 카운터를 낸다. 격자(쿼리 패턴 × 규모 × 버퍼풀 크기 × 키 분포)를 돌릴 재료가 다 있다.
- **발생 가능한 문제** (2단계 관측 신호):
  - **카운터 정확성은 pool 단위 테스트만 지킨다**: diff 12 변이에서 MRU·핀 무시는 인덱스 테스트에서 전부 생존(결과만 BTreeMap 대조). 벤치마크 수치는 카운터에 기대므로, 인덱스 연산 단위의 기대 I/O 수 테스트가 없으면 측정 버그가 조용히 섞인다.
  - **Hash `range`는 모든 버킷을 읽는다**(`buckets()` → 거름 → 정렬, `Vec` 반환 유지). 범위 조회 격자에서 Hash는 결과 크기와 무관하게 전체 스캔 — 의도된 비교 대상이지만 10^7에서 메모리·시간이 커질 수 있다.
  - **디렉터리 두 배 비용**: 칸 2048 초과부터 디렉터리 페이지 통째 복사(쓰기 카운트 스파이크) — 4단계 "더블링 스파이크" 실험의 신호이자 3단계 랜덤 삽입 수치의 잡음원.
  - **전역 깊이 상한 21**(메타 2044 × 2048칸): 10^7 키 · 작은 bucket_cap이면 근접 가능 → `Err`. 격자 설정 전에 cap별 필요 깊이 계산.
  - **속도**: 매 삽입 `check()` 속성 테스트가 이미 16~24s(debug). 벤치마크는 release · check 없이, 측정 루프와 검증 루프를 분리.
- **방법론 선택지**:

| 방안 | 요지 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|----------|----------|
| A | `Index` trait + 풀 `io_counts()`/`stats()` 스냅샷 차이로 측정하는 자체 러너(bin) | 작음 | 실행 시간 측정 잡음 | I/O 수가 주 지표일 때(README 기대 결과) |
| B | criterion 도입 | 중간 | 새 의존성 · I/O 카운터와 결합 어색 | 실행 시간 분포가 주 지표일 때 |

- **권장 대처**: A로 시작(새 의존성 없음). 첫 diff에 "연산 하나의 기대 read/write 수" 테스트를 먼저 넣어 카운터 공백을 메운다.
- **착수 전 확인할 것**: 격자 축 축소 범위(10^7 포함 여부) · 결과 형식(CSV/표) · 파일 저장소(실제 디스크) vs 메모리 저장소.

# index-lab

페이지 기반 스토리지 엔진 위에서 인덱스 구조(B+tree, Hash 등)를 교체하며
**쿼리 패턴 × 데이터 규모 × 버퍼풀 크기**에 따른 성능 차이를 실측하는 실험 프로젝트.

## 목적

RDBMS는 왜 B-tree를 기본 인덱스로 쓰는가?
해시는 동등 조회에서 더 빠른데 왜 기본이 아닌가?
데이터 유형과 워크로드에 따라 어떤 인덱스를 골라야 하는가?

이 질문에 "설명"이 아니라 **직접 구현한 엔진의 측정값**으로 답하는 것이 목표다.
측정 핵심 지표는 실행 시간이 아니라 **디스크 페이지 읽기/쓰기 횟수**다.

## 범위

### 포함
- 고정 크기 페이지(16KB) 기반 파일 I/O 계층 (Pager)
- 고정 프레임 수 + LRU 버퍼풀 (크기 조절 가능)
- `Index` trait 과 그 구현체
  - B+tree (리프 연결 리스트 포함, fan-out 조절 가능)
  - Hash (extendible hashing)
  - 추가 예정: BRIN 유사 블록 범위 인덱스
- 벤치마크 하네스: 워크로드 생성 → 실행 → CSV 출력
- 결과 시각화 스크립트

### 제외
- SQL 파서, 쿼리 플래너
- 트랜잭션, WAL, 복구
- 동시성 제어
- 가변 길이 레코드 (키는 `u64`, 값은 고정 길이)

## 실험 설계

| 축 | 값 |
|---|---|
| 쿼리 패턴 | 동등 조회 / 범위 조회 / 순차 삽입 / 랜덤 삽입 |
| 데이터 규모 | 10^5 / 10^6 / 10^7 건 |
| 버퍼풀 크기 | 데이터 전체 적재 / 50% / 10% |
| 키 분포 | 단조 증가 / 균등 랜덤 / 편중(Zipf) |

각 조합에 대해 B+tree 와 Hash 를 동일 조건으로 실행하고
page read 수, page write 수, 트리 깊이(해당 시), 실행 시간을 기록한다.

추가 실험
- B+tree fan-out 변경(4 → 64 → 512)에 따른 깊이와 I/O 변화
- Hash 디렉토리 더블링 시점의 쓰기 비용 스파이크
- 풀스캔 후 버퍼풀 오염이 인덱스 조회에 미치는 영향

## 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Rust (stable) | GC 없음, 페이지 바이트 레이아웃 직접 제어, 소유권으로 버퍼풀 버그 방지 |
| 파일 I/O | `std::fs` + `read_at` / `write_at` | mmap 을 피해 OS 페이지 캐시 영향을 줄이고 I/O 횟수를 직접 계수 |
| 바이트 처리 | `bytemuck` | 페이지 버퍼 ↔ 구조체 캐스팅 |
| 벤치마크 | `criterion` + 자체 카운터 | 시간 측정은 criterion, I/O 횟수는 Pager 내장 카운터 |
| 워크로드 생성 | `rand`, `rand_distr` | 균등 / Zipf 분포 |
| 결과 출력 | `csv`, `serde` | 실험 결과 직렬화 |
| 시각화 | Python (`pandas`, `matplotlib`) | 그래프 생성 |
| 테스트 | `proptest` | 삽입/조회 무작위 속성 테스트 |

## 구조

```
index-lab/
├── src/
│   ├── pager.rs        # 페이지 단위 파일 I/O, read/write 카운터
│   ├── buffer_pool.rs  # 프레임 관리, LRU
│   ├── index/
│   │   ├── mod.rs      # trait Index { insert, get, range }
│   │   ├── btree.rs    # B+tree
│   │   └── hash.rs     # extendible hashing
│   └── bench/
│       ├── workload.rs # 쿼리/키 생성
│       └── runner.rs   # 실험 조합 실행, CSV 기록
├── scripts/
│   └── plot.py
├── results/
└── README.md
```

## 로드맵

1. 메모리 내 B+tree, Hash 구현 및 속성 테스트
2. Pager + 버퍼풀 구현, 인덱스를 페이지 위로 이동
3. 벤치마크 하네스, 기본 격자 실험
4. fan-out / 디렉토리 더블링 / 캐시 오염 추가 실험
5. 결과 분석 및 "워크로드별 인덱스 선택 가이드" 정리

## 기대 결과

- 데이터가 버퍼풀을 넘는 지점에서 Hash 의 랜덤 I/O 가 급증하는 그래프
- 범위 조회에서 B+tree 리프 연결의 효과
- fan-out 증가에 따른 트리 깊이 감소와 I/O 감소의 관계
- 키 분포(단조/랜덤)에 따른 삽입 비용 차이
